# Benchmarks

Every number on this page comes from a JSON file in [`results/`](../results), written by `npm run bench`.

## Method

Each run does what WordPress does for one uploaded image: it makes every default image size from the original and encodes each one.

| Size | Box | Crop |
|---|---|---|
| thumbnail | 150 × 150 | yes |
| medium | 300 × 300 | no |
| medium_large | 768 wide | no |
| large | 1024 × 1024 | no |
| 1536x1536 | 1536 × 1536 | no |
| 2048x2048 | 2048 × 2048 | no |

- **Encoding:** the same options as `@wordpress/vips` in WordPress 7.2: JPEG quality 82, WebP quality 86, AVIF quality 52 with effort 2, ICC profiles kept. Most runs encode JPEG and WebP (12 outputs). The AVIF runs add AVIF (18 outputs).
- **Inputs:** `images/input.jpg` (6000 × 4000, 24 MP) and `images/input-8660x5773.jpg` (50 MP), generated by `npm run images`.
- **Timing:** one warm-up batch, then 5 timed batches (3 for the 50 MP input). The tables show the median. Start-up time is measured separately.
- **Workers:** with more than one worker, the tasks are spread round-robin over that many workers, each with its own wasm-vips instance. WordPress uses one worker.
- **Heap:** the size of each instance's WebAssembly memory after the run, which starts at 256 MiB and grows as needed.
- **Machine:** Apple M3 (8 cores), macOS 15.8.2, Node 24.22.1, Playwright 1.64.0 with Chromium 156, Firefox 157 and WebKit (Safari 27.2).

The builds:

| Name | What it is |
|---|---|
| npm | The published wasm-vips 0.0.19 package |
| baseline | The same release built from source here, with threads |
| nothreads | The same commit built without threads |

In the browser tables, npm and baseline run on a cross-origin isolated page, since they need it. nothreads runs on a plain page without isolation. Browsers run every build with libvips concurrency 1, which the release build sets on the web.

## Phones

The [published pages](https://b1ink0.github.io/wasm-vips-nothreads/) with the 24 MP input, opened once per setup on a Samsung Galaxy S26 Ultra and an iPhone 17 Pro on 25 November 2026. Each cell is the median of 5 batches. The numbers were read from screenshots of the pages, so there is no file in `results/` for them, and the browser versions were not recorded. Every browser on iOS uses WebKit.

| Phone | Browser | nothreads, 1 worker, plain page | baseline, 1 worker, isolated page | nothreads, 4 workers with AVIF, plain page | baseline, 4 workers with AVIF, isolated page |
|---|---|---|---|---|---|
| Galaxy S26 Ultra | Chrome | 2272 ms | 2454 ms | 2008 ms | 2751 ms |
| | Firefox | 2283 ms | 3268 ms | 2260 ms | 2607 ms |
| | Samsung Internet | 4083 ms | 2903 ms | 2147 ms | Not run |
| iPhone 17 Pro | Safari | 1598 ms | 1591 ms | 1599 ms | 1608 ms |
| | Chrome | 1616 ms | 1614 ms | 1660 ms | 1600 ms |
| | Firefox | 1641 ms | 1599 ms | 1702 ms | 1668 ms |

- Every run finished. On the plain page every browser reported `crossOriginIsolated` and `SharedArrayBuffer` as false, and the build without threads still ran.
- On the iPhone, the two builds are within 3% of each other in every browser.
- On the Galaxy, the build without threads was faster than the release build in Chrome and Firefox. The 4083 ms run in Samsung Internet spread from 2511 to 4569 ms, so it is not a steady number.
- With four workers and AVIF, the heaps added up to 1136.75 MiB for the build without threads and 1323.25 MiB for the release build on both phones, as on the desktop.
- For the first output, `1536x1536.jpeg`, the part of the SHA-256 visible in the screenshots is the same in both builds in Chrome and Firefox on the Galaxy, and matches the desktop output.
- The release build on the plain page was not run on the phones.

## Release build without isolation

On the plain page, the baseline build fails in every browser:

- Chromium and Firefox: start-up does not finish within 60 seconds.
- WebKit: start-up finishes, then the first image throws a `WebAssembly.Exception` (a C++ exception from inside the module).

## Node

Node needs no isolation, so it compares the builds with libvips' own thread pool too. "c8" is the default concurrency on this machine, "c1" is concurrency 1 as on the web.

| Run | 24 MP, JPEG and WebP | 24 MP, with AVIF | 50 MP, JPEG and WebP |
|---|---|---|---|
| npm, c8 | 1725 ms | 3460 ms | |
| baseline, c8 | 1736 ms | 3623 ms | 2229 ms |
| baseline, c1 | 1794 ms | 3532 ms | 2358 ms |
| nothreads | 1866 ms | 3819 ms | 2371 ms |
| baseline, c1, 4 workers | 714 ms | 2193 ms | 1226 ms |
| nothreads, 4 workers | 770 ms | 1873 ms | 1642 ms |

nothreads with 2 and 6 workers on the 24 MP JPEG and WebP run: 1233 ms and 738 ms.

One 2048 px JPEG from the 50 MP input, the case a thread pool helps most: 222 ms (baseline, c8) and 236 ms (nothreads).

## Output

Every JPEG and WebP output has the same SHA-256 in every run: all three builds, Node and all three browsers. AVIF outputs are identical in every run with concurrency 1, which covers every browser run. Only the Node runs with concurrency 8 produce different AVIF bytes.
